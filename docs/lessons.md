# 踩坑记录

单人维护一套生产系统，坑全是自己踩自己填。每条按「现象→诊断→解法」写，都是真实事故。

## 1.（2026-09）微信 iLink 时段限流：凌晨 cron 推送全灭

**现象**：某天早上发现头天夜里所有 cron 定时推送全 failed，微信上一条没收到。白天任务又一切正常。

**诊断**：拿 `deliveries.db` 按天聚合失败分布，发现失败全部集中在深夜时段、且集中在微信通道，飞书通道同时段正常——不是网络问题，是微信通道（iLink）的时段限流。再用 grep 扫网关日志确认：深夜批量推送时通道直接拒绝，不是超时。

**解法**：不跟限流硬刚。深夜 cron 的 `deliver` 改成 `local`（本地落盘），另加一个早上的兜底任务翻查未投递记录补推。代价是消息晚到几小时，换来 100% 触达。教训：**第三方通道的隐式限流要当一等公民设计，投递必须可补**。

## 2.（2026-08）双 gateway 抢 token：重复推送

**现象**：微信每条消息回复两次，cron 推送也成对出现。

**诊断**：查进程发现两个网关实例同时在跑。根因是两个 gateway 配置都指向同一个微信通道，抢同一个 token，轮询各自独立——同一条消息被两边各消费一次。

**解法**：通道唯一化。一个通道只允许一个 gateway 实例持有，另一个实例改配别的通道或禁用；systemd 里显式管理实例数，避免手动起进程造成双活。**验证**：停掉多余实例观察 24h，重复推送消失，确认因果。教训：**单通道单持有者，靠约定不如靠进程管理**。

## 3.（2026-09）docx blocks API「诈包」：GET 200 但 POST 同路径 404

**现象**：往飞书云文档写块，POST 到某个 blocks 路径一直 404。但同样的路径 GET 是 200——路径明明存在。

**诊断**：对比官方文档发现，GET 和 POST 支持的路径形态不同：对「文档级 blocks 集合」POST 写块必须落在**文档根块 ID** 的路径上，而不是文档 ID 路径。GET 对两种路径都宽容，POST 只认块 ID 路径——这就是「诈包」：GET 通了让人误以为路径没问题。

**解法**：写块前先 GET 拿到根块 ID，POST 一律走 `/documents/{doc_id}/blocks/{block_id}/children` 这种块 ID 路径。封装成一个写文档的函数后没再踩过。教训：**REST API 的 GET 成功不等于 POST 可用，写操作按最严格路径形态来**。

## 4.（2026-08）cron prompt 批量修改：CLI 静默不落盘

**现象**：批量调整 19 个 cron 任务的 prompt，用 CLI 逐个编辑后，部分任务实际没改——执行时还是旧 prompt，但 CLI 当时没报错。

**诊断**：直接读 `jobs.json` 对比，确认部分字段没写进去。结论：CLI 的批量编辑路径有静默失败前科，不可信。根因未深究（可能并发写或缓存问题），改 Python 直写 + 读回绕过。

**解法**：批量修改一律用 Python 直接改 `jobs.json`，改完**读回验证**（diff 确认每个目标字段已落盘）再收工。教训：**批量变更必须有「写后读回」闭环，不能信工具的 exit 0**。

## 5.（2026-10）cron drift_skip：模型漂移保护

**现象**：某些定时任务偶尔「跳过」执行，日志里带 drift 标记，像随机丢任务。

**诊断**：这是调度器的漂移保护机制：当任务执行时刻相对计划时刻漂移超过阈值（实测 drift 4700ms > 阈值 3000ms），直接 skip 本轮，防止任务堆积雪崩。

**解法**：理解机制后把它当特性用：重任务控制单次执行时长、错峰排布；真正要保时保量的任务拆成更小的子任务。**调度器的「丢任务」往往是保护动作，先读日志确认语义再治理**。

## 6.（2026-11）59G 小盘治理：journal 压缩 / snap / 缓存

**现象**：59G 的小系统盘告警磁盘 >90%，健康监控开始骚扰。

**诊断**：`du` 分层排查，大头依次是：systemd journal 日志（无限增长）、snap 包多版本残留、各路缓存（pip/npm/浏览器）。

**解法**：按「安全优先级」清理：
1. journal 限流：`SystemMaxUse=200M` + 压缩，一劳永逸；
2. snap 老版本：保留最近 2 版，其余 `snap remove --revision` 清掉；
3. 包管理器缓存直接清；
4. Docker 日志限额（有容器时）`max-size` 拦在前面。

再加一条 cron 定期清，配合监控告警阈值 90%。教训：**小盘机器日志和缓存必须有硬上限，靠人肉清理必翻车**。

## 7.（2026-11）同步链路上笔记被误删：投递账号权限过大

**现象**：Obsidian 同步链路上发现笔记被误删，且不是人为操作。

**诊断**：审计整条写路径（投递脚本 → outbox 库 → CouchDB 复制 → 主库），发现投递用的账号权限过大——能写主库，也就意味着能删。

**解法**：换专用最小权限 outbox-writer 账号：主库只读，只写 outbox 库，只写不删。投递通道在物理上失去删主库数据的能力。教训：**投递账号的最小权限不是优化项，是事故防线——能删的账号迟早会删**。

## 8.（2026-11）待办权威源迁移：双写 = 数据事故

**现象**：待办数据同时记在两套系统里（一张聚合表 + 各处散写），出现口径分叉：同一件事两边状态不一致，事后说不清哪个是准的。

**诊断**：盘点全部写入端，发现迁移到新清单系统后，旧系统的写入通道没有显式封死，还有 cron 在往里写——「启用了新的」不等于「停掉了旧的」。

**解法**：一次性定死权威源：旧聚合表冻结留档（只读，禁止再写），旧的本机台账文件改名加 `.retired` 后缀让任何脚本都写不进去，写入路由收敛成一条白名单通道。教训：**权威源迁移的关键动作不是「启用新」，是「封死旧」——留着能写的旧通道，迟早双写**。

## 9.（2026-11）事实断言闸：闲聊里编出来的细节最伤信任

**现象**：助手在轻松闲聊场合顺口输出了几条「听起来合理」的事实细节（地点风物、人物、时间安排），其中一部分是编的，被当面抓包。一天之内连出六条。

**诊断**：复盘发现共同模式：越是闲聊越没走实查——正式任务有工具闸，闲聊接梗反而「凭印象」直接说。而且 LLM 编造时的语气和实查结果完全一样，接收方无法分辨。

**解法**：立一条全人格生效的硬闸：时效性数字 + 与维护者个人相关的事实（行程/安排/人物/前提），开口前必须实查或读账，查不到就明说「凭印象待核」；再加一个夜间对账 cron 交叉核对「说过的 vs 落地的」。教训：**恢复诚实救不回信任，拦截必须发生在发送前；闲聊不是豁免，是高危场景**。

## 10.（2026-11）模型降本分流：切换必须带探活门禁

**现象**：为控成本把主力模型切到低价 flash 档。直接切的风险是：新档位要真不可用，所有 cron 和对话一起静默降级。

**诊断**：模型路由变更和代码部署同构——没有 health check 的切换就是在裸奔。另外此前的「自动切换」链路（挂了自动换下一家）从未做过故障演练，不敢开。

**解法**：手动切换脚本先对新端点发探活请求，通过才改配置；自动切换 cron 全部暂停，兜底顺序写死在文档里（flash → 备份 flash），等演练过再开。教训：**省钱降档可以，但换模型 = 换生产依赖，探活门禁和手动回退路径缺一不可**。

## 11.（2026-11）子代理并行派活：一个 key 挂，N 个任务同时挂

**现象**：一次派 4 个并行子任务调研，几秒内全部返回，每个 summary 都是「API key 无效」的报错文案——不仔细看会当成「调研结果都很短」收下。

**诊断**：并行子任务共用同一个上游 provider，key 失效导致全部 401，且 fanout 框架把错误文案塞进了 summary 字段，成功和失败在结构上长得一样。

**解法**：fanout 返回后先逐个验 `status` / `error` 字段再读内容，全败时主线程直接接管自己跑；key 有效性纳入日常巡检。教训：**并行派活的失败是同源同时的，别把错误文案当结果；收活先看状态码，再看内容**。
