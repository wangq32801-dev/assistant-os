# 踩坑记录

单人维护一套生产系统，坑全是自己踩自己填。每条按「现象→诊断→解法」写，都是真实事故。

## 1. 微信 iLink 时段限流：凌晨 cron 推送全灭

**现象**：某天早上发现头天夜里所有 cron 定时推送全 failed，微信上一条没收到。白天任务又一切正常。

**诊断**：拿 `deliveries.db` 按天聚合失败分布，发现失败全部集中在深夜时段、且集中在微信通道，飞书通道同时段正常——不是网络问题，是微信通道（iLink）的时段限流。再用 grep 扫网关日志确认：深夜批量推送时通道直接拒绝，不是超时。

**解法**：不跟限流硬刚。深夜 cron 的 `deliver` 改成 `local`（本地落盘），另加一个早上的兜底任务翻查未投递记录补推。代价是消息晚到几小时，换来 100% 触达。教训：**第三方通道的隐式限流要当一等公民设计，投递必须可补**。

## 2. 双 gateway 抢 token：重复推送

**现象**：微信每条消息回复两次，cron 推送也成对出现。

**诊断**：查进程发现两个网关实例同时在跑。根因是两个 gateway 配置都指向同一个微信通道，抢同一个 token，轮询各自独立——同一条消息被两边各消费一次。

**解法**：通道唯一化。一个通道只允许一个 gateway 实例持有，另一个实例改配别的通道或禁用；systemd 里显式管理实例数，避免手动起进程造成双活。教训：**单通道单持有者，靠约定不如靠进程管理**。

## 3. docx blocks API「诈包」：GET 200 但 POST 同路径 404

**现象**：往飞书云文档写块，POST 到某个 blocks 路径一直 404。但同样的路径 GET 是 200——路径明明存在。

**诊断**：对比官方文档发现，GET 和 POST 支持的路径形态不同：对「文档级 blocks 集合」POST 写块必须落在**文档根块 ID** 的路径上，而不是文档 ID 路径。GET 对两种路径都宽容，POST 只认块 ID 路径——这就是「诈包」：GET 通了让人误以为路径没问题。

**解法**：写块前先 GET 拿到根块 ID，POST 一律走 `/documents/{doc_id}/blocks/{block_id}/children` 这种块 ID 路径。封装成一个写文档的函数后没再踩过。教训：**REST API 的 GET 成功不等于 POST 可用，写操作按最严格路径形态来**。

## 4. cron prompt 批量修改：CLI 静默不落盘

**现象**：批量调整 19 个 cron 任务的 prompt，用 CLI 逐个编辑后，部分任务实际没改——执行时还是旧 prompt，但 CLI 当时没报错。

**诊断**：直接读 `jobs.json` 对比，确认部分字段没写进去。结论：CLI 的批量编辑路径有静默失败前科（可能并发写或缓存问题），不可信。

**解法**：批量修改一律用 Python 直接改 `jobs.json`，改完**读回验证**（diff 确认每个目标字段已落盘）再收工。教训：**批量变更必须有「写后读回」闭环，不能信工具的 exit 0**。

## 5. cron drift_skip：模型漂移保护

**现象**：某些定时任务偶尔「跳过」执行，日志里带 drift 标记，像随机丢任务。

**诊断**：这是调度器的漂移保护机制：当任务执行时刻相对计划时刻漂移超过阈值（比如上一次执行拖太久），直接 skip 本轮，防止任务堆积雪崩。

**解法**：理解机制后把它当特性用：重任务控制单次执行时长、错峰排布；真正要保时保量的任务拆成更小的子任务。**调度器的「丢任务」往往是保护动作，先读日志确认语义再治理**。

## 6. 59G 小盘治理：journal 压缩 / snap / 缓存

**现象**：59G 的小系统盘告警磁盘 >90%，健康监控开始骚扰。

**诊断**：`du` 分层排查，大头依次是：systemd journal 日志（无限增长）、snap 包多版本残留、各路缓存（pip/npm/浏览器）。

**解法**：按「安全优先级」清理：
1. journal 限流：`SystemMaxUse=200M` + 压缩，一劳永逸；
2. snap 老版本：保留最近 2 版，其余 `snap remove --revision` 清掉；
3. 包管理器缓存直接清；
4. Docker 日志限额（有容器时）`max-size` 拦在前面。

再加一条 cron 定期清，配合监控告警阈值 90%。教训：**小盘机器日志和缓存必须有硬上限，靠人肉清理必翻车**。
